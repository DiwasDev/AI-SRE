## Detailed Evaluation & Model Comparison

### Session 1: Core Trust, Prompt Security & Failure Modes (Q5.1–Q5.13)

#### Q5.1: Prompt Injection via Application Logs
- **What the Team Said:** Logs are data only, never instructions. Kashyap noted logs have a "data role" and instruction-like text should be discarded. You raised that the agent might search the web based on logs and untrusted links must not be followed.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* Application logs are untrusted input and cannot override platform rules or authorize actions; external links inside logs must never be followed automatically.
  - *Disagreed:* Claude highlighted the operational choice between silently dropping injected lines vs. alerting an engineer, whereas GPT framed the open decision around flagging, ignoring the snippet, or rejecting the entire log payload.
- **Approved Decision Record:** Treat all logs as passive, delimited data (`UNTRUSTED_EXTERNAL_DATA`). Block outbound URL fetching from logs (reinforced in Q5.16) and flag suspicious lines rather than silently dropping evidence (reinforced in Q5.23).

#### Q5.2: Untrusted Instructions & Data in Same Context Window
- **What the Team Said:** Team treated Q5.2 as identical to Q5.1. You stressed separating internal system instructions from external application data.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* Authority comes from the platform's fixed source, never from formatting inside retrieved context.
  - *Disagreed:* Claude explained *why* Q5.2 is distinct—compromised tools, ticket descriptions, or API payloads can inject instruction-like text outside of logs—and proposed a strict blanket rule downgrading everything outside hard-coded platform prompts to data. GPT focused primarily on prompt separation and adversarial test cases.
- **Approved Decision Record:** Source-based binary trust: only hard-coded platform prompts are instructions; all tool outputs, logs, and tickets are untrusted data.

#### Q5.3: Model Generates Destructive Shell Command
- **What the Team Said:** Unanimous that the model never executes write or destructive commands. You proposed the "harness" pattern: model emits structured schema requests; harness validates against a read-only allow-list.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* Zero direct shell access, zero autonomous writes, deterministic harness validation, single human approval gate for prod changes.
  - *Disagreed:* Claude specified auto-rejecting invalid schemas without model retry loops; GPT emphasized defining whether read-only commands require approval and which environments they touch.
- **Approved Decision Record:** Model emits structured schemas only; Execution Harness validates every request against a predefined allow-list of read-only commands (plus Monitoring + Git read-only). Zero arbitrary shell or unapproved prod writes.

#### Q5.4: Confidently Incorrect Diagnosis
- **What the Team Said:** Team drifted into talking about requiring evidence (Q5.5) and briefly noted wrong diagnosis leads to more downtime. You noted structured, verifiable output is needed.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* Confident wrong diagnoses can lead humans to approve unsafe fixes. Supporting evidence is mandatory.
  - *Disagreed:* Claude traced the exact causal failure chain (wrong diagnosis + confident tone $\rightarrow$ human rubber-stamps unsafe fix $\rightarrow$ prolonged outage or secondary breakage). GPT focused on gating fix generation until evidence is present.
- **Approved Decision Record:** Link every diagnosis to concrete, reproducible telemetry artifacts; retry up to **3 times** if evidence is missing before blocking fix generation and escalating.

#### Q5.5: Evidence Requirement for Diagnoses *(Claude Q5.5 / GPT flagged missing)*
- **What the Team Said:** Team answered under Q5.4: every diagnosis needs evidence; more evidence gives higher reviewer confidence.
- **Claude vs. ChatGPT Comparison:** Claude extracted this as Q5.5 and proposed explicit confidence tiers (`High` / `Medium` / `Low`) plus a minimum 1-artifact rule. GPT marked Q5.5 unanswered in the transcript.
- **Approved Decision Record:** Require qualitative confidence ratings, $\ge 1$ timestamped evidence artifact, and explicit surfacing of weak/contradictory evidence.

#### Q5.6: Unauthorized User Attempts Action *(Claude Q5.6 / GPT Q5.7)*
- **What the Team Said:** Rule-based authorization; reject unauthorized users and inform them. Password login was mentioned casually.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* RBAC enforcement with explicit rejection and audit logging.
  - *Disagreed:* Claude explicitly rejected standalone passwords as inadequate for production SRE systems, mandating existing company SSO/IAM. GPT also advised using an existing identity provider.
- **Approved Decision Record:** Enforce **email and password**-backed RBAC (`Viewer` / `Approver` / `Administrator` per Q5.20–Q5.24) and log every rejected attempt.

#### Q5.8: Post-Approval Patch Modification *(User-supplied Q5.8 text / GPT Q5.8 / Claude Q5.7)*
- **What the Team Said:** Git-like patch versioning with a hash/fingerprint so any post-approval edit invalidates approval. **User's answer:** Use a hash to detect differences in paths and configuration values between the approved version and executed version.
- **Claude vs. ChatGPT & Critique of User Answer:**
  - *Agreed:* Hash at approval, re-hash before execution, abort and require re-approval on mismatch.
  - *Critique (without overengineering):* Hashing *paths* or *config values alone* misses content changes inside the same file path or non-config code edits. Keep it simple: serialize and hash the **exact canonical unified diff bytes** (plus target file path + base commit SHA) with SHA-256 at approval time, store the exact bytes + hash in Postgres, and have the `AI Deployment Executor` verify `sha256(bytes_to_apply) == approved_hash` immediately before rollout (fail-closed, no custom version-control engine needed).
- **Approved Decision Record:** Compute SHA-256 of canonical patch bytes + target path + base commit SHA at human approval; `AI Deployment Executor` verifies exact hash match pre-deploy and aborts/invalidates on mismatch.

#### Q5.9: Production Credentials & Environment Variables
- **What the Team Said:** Model must never hold raw secrets. Kashyap suggested masking/hashing; you proposed that the harness fetches/injects real secrets out-of-band at execution time.
- **Claude vs. ChatGPT Comparison:** Both models agreed completely and corrected Kashyap's suggestion: hashing/masking doesn't work when an operation needs real credentials to authenticate. Secret isolation via alias + harness injection is required.
- **Approved Decision Record:** Model references secret aliases only; Execution Harness retrieves secrets from a secrets store at runtime; stdout/stderr redacted before returning to model.

#### Q5.10: Duplicate Execution After Retry
- **What the Team Said:** Duplicate actions cause duplicate data, inconsistent state, repeated operations, and higher cost; every action must be tracked.
- **Claude vs. ChatGPT Comparison:**
  - *Agreed:* Track every action with unique IDs and check status before retrying.
  - *Disagreed:* Claude differentiated action types (idempotent config revert vs. non-idempotent double service restart); GPT focused on handling uncertain first-attempt outcomes.
